Zoho Cliq GitHub Informer

This document summarizes how the two repositories work together: one repository provides the reusable GitHub Action implementation, and the other provides the ready-to-use workflow template that consuming repositories can copy and configure.

Action Repo: GitHub-Informer-New Template Repo: TemplateRepositoryNew Features: Cliq notifications + Project thread reuse + AI review gate
Repository 1

GitHub-Informer-New

This is the reusable public GitHub Action. It contains the Java implementation that:

  • posts GitHub event notifications to Zoho Cliq,
  • supports user mode and bot mode,
  • stores and reuses Cliq thread IDs in GitHub Project V2,
  • runs the AI Review Gate and publishes a check run.
Open GitHub-Informer-New repository
Repository 2

TemplateRepositoryNew

This is the workflow template repo. It contains the ready-made .github/workflows/CliqConnector.yml file that consuming repositories can use directly.

  • wires secrets and variables into the action,
  • handles PR project pre-insert logic,
  • configures AI review inputs,
  • builds the final Cliq endpoint for user or bot mode.

Recommended Model

How Both Repositories Are Used

  1. Publish and version the action from GitHub-Informer-New using a tag such as v3.
  2. Keep the workflow template in TemplateRepositoryNew.
  3. In a consuming repository, copy CliqConnector.yml or use it as the reference workflow.
  4. Configure repository Secrets and Variables.
  5. The workflow calls Lincy-Zoho/GitHub-Informer-New@v3.
Best practice: users should not copy action source files locally. They only need the workflow file in their repo, while the action logic stays in the public action repo.
Setup Flow

Quick Overview: Steps To Go Live

  1. Add the workflow file (copy CliqConnector.yml) to .github/workflows/ in the consuming repository. No separate branch needs to be created for this.
  2. Set the four configuration Variables (CLIQ_NOTIFICATION_MODE, CLIQ_BOT_UNIQUE_NAME, CLIQ_PROJECT_NUMBER, CLIQ_THREAD_FIELD_ID) under Settings → Secrets and variables → Actions → Variables, only if you need bot mode or project thread reuse — all are optional with safe defaults.
  3. Create a protected Environment (e.g. cliq-production) and add ENDPOINT, PROJECT_TOKEN, and (if AI review is enabled) AI_REVIEW_TOKEN as Environment secrets. The AI provider endpoint and model are plain workflow inputs, not secrets.
  4. Run the workflow once on a real pull request so GitHub registers the ai-review-check-name check context.
  5. Add that exact check name as a required status check in Branch Protection or Rules.
  6. Push a new commit (or re-run) so the newly required check is enforced going forward.
GITHUB_TOKEN is provided automatically by GitHub Actions for every run — it is never configured manually as a secret.
Setup

Required Secrets and Variables

ENDPOINT, PROJECT_TOKEN, and AI_REVIEW_TOKEN should be stored as Environment secrets inside a protected environment (e.g. cliq-production) so only Admins/required reviewers can view or edit them — not as plain repository secrets. See the main README's "Add Secrets via a Protected Environment" section for full setup steps.
Name Type Purpose
ENDPOINT Environment secret Cliq channel endpoint with ?zapikey=...
PROJECT_TOKEN Environment secret Classic GitHub PAT for Project V2 operations. Required scopes: repo, project, and optionally read:org for org-owned projects.
AI_REVIEW_TOKEN Environment secret Token for OpenAI, Claude, or Gemini if AI review is enabled.
CLIQ_NOTIFICATION_MODE Variable or YAML value user or bot
CLIQ_BOT_UNIQUE_NAME Variable or YAML value Required only for bot mode.
CLIQ_PROJECT_NUMBER Variable — required, no default GitHub Project V2 number, e.g. the 1 in https://github.com/orgs/<orgname>/projects/1. Maps internally to GITHUB_PROJECT_NUMBER in the workflow env. You must create this variable yourself.
CLIQ_THREAD_FIELD_ID Variable — required, no default Project field identifier or GraphQL field node id used to store the Cliq thread id. Maps internally to GITHUB_PROJECT_THREAD_FIELD_ID in the workflow env. You must create this variable yourself.
Note: the four names above (CLIQ_NOTIFICATION_MODE, CLIQ_BOT_UNIQUE_NAME, CLIQ_PROJECT_NUMBER, CLIQ_THREAD_FIELD_ID) are the GitHub Actions Variable names you set once under Settings → Secrets and variables → Actions → Variables. The workflow reads them via vars.* and passes them into the action under slightly different internal env names (shown above) — you never need to edit CliqConnector.yml to set these.
Notification Modes

User Mode vs Bot Mode

Mode What User Sets Notes
User mode CLIQ_NOTIFICATION_MODE=user Uses the existing ENDPOINT secret as-is. No bot unique name is required.
Bot mode CLIQ_NOTIFICATION_MODE=bot
CLIQ_BOT_UNIQUE_NAME=<bot-name>		 The workflow reuses ENDPOINT and appends bot_unique_name automatically.

Two Supported Ways to Provide Mode Values

  1. GitHub Variables in repository settings.
  2. Direct values in CliqConnector.yml.
env:
  CLIQ_NOTIFICATION_MODE: ${{ vars.CLIQ_NOTIFICATION_MODE || 'user' }}
  CLIQ_BOT_UNIQUE_NAME: ${{ vars.CLIQ_BOT_UNIQUE_NAME || '' }}
Recommended approach: use GitHub Variables for CLIQ_NOTIFICATION_MODE and CLIQ_BOT_UNIQUE_NAME, because users can change them without editing the workflow file.
Bot Setup

How to Configure Bot Mode in Zoho Cliq

  1. Create the bot in Zoho Cliq.
  2. Open Integrations -> Bots.
  3. Select the bot you created.
  4. In the bot details panel, check the API Endpoint.
  5. The value after /bots/ is the bot unique name.
  6. Add the bot to the target Cliq channel.
Example API endpoint:
https://cliq.zoho.com/api/v2/bots/githubnotification/message

Bot unique name:
githubnotification
Project Reuse

How Cliq Thread Reuse Works

  1. The action resolves the PR item in GitHub Project V2.
  2. It reads the existing value from the configured custom field.
  3. If no thread id exists, it posts a new Cliq message.
  4. It extracts the returned message_id.
  5. It saves that id in the Project V2 custom field.
  6. Later PR events reuse the same thread.
AI Review

Enabling the AI Service Model

AI review is off by default. To turn it on, set the ai-review-enabled workflow input to true and configure a provider, token, and model. The provider (OpenAI, Claude, or Gemini) is not a separate setting — it is chosen via the ai-review-api-url/ai-review-model you pick together with the matching token.

Input Purpose
ai-review-enabled Set to true to turn on the AI review gate for pull requests.
ai-review-token AI provider token, backed by an Environment secret (not a repository secret), e.g. ${{ secrets.AI_REVIEW_TOKEN }}.
ai-review-api-url Endpoint for the chosen provider (OpenAI, Claude, or Gemini).
ai-review-model Model name to use, e.g. gpt-4.1-mini, claude-3-5-sonnet-latest, or gemini-1.5-pro. Falls back to a per-service default if omitted. 
with:
  ai-review-enabled: true
  ai-review-token: ${{ secrets.AI_REVIEW_TOKEN }}
  ai-review-api-url: https://api.openai.com/v1/chat/completions
  ai-review-model: gpt-4.1-mini

Optional: Enable via Config File Instead

If you'd rather toggle AI review from a plain file than from workflow inputs, set ai-review-config-file to a path in your repo and add an ai_review: block:

ai_review:
  enabled: true
  service: openai   # openai | claude | gemini
  model: gpt-4.1-mini   # optional
When the config file and its ai_review block are found, enabled and service from the file take precedence over the ai-review-enabled workflow input and automatic provider detection. The AI token is still never read from this file — it always comes from the ai-review-token input.
AI Review

AI Review Gate Flow

  1. The workflow runs AI review on pull_request_target.
  2. The action fetches PR diff, sends it to the configured AI provider, and parses the result.
  3. It creates a GitHub check run using ai-review-check-name.
  4. If the AI result is PASS, merge can proceed.
  5. If the AI result is FAIL, the PR gets a comment and the Cliq PR thread receives the failure report.

Required Status Check Setup

  1. Set the workflow input ai-review-check-name to the desired check name (defaults to AI Review Gate if not set).
  2. Run the workflow once on a PR so GitHub registers the check context.
  3. In GitHub Rules or Branch Protection, enable Require status checks to pass.
  4. Add the exact same check name as a required check.
  5. Push a new commit or re-run the workflow so the newly required check is picked up.
Exact name matching matters. If the required check name and the workflow check name differ, GitHub shows Waiting for status to be reported.
Workflow Shape

High-Level Execution Flow

  1. Resolve mode and prepare Cliq endpoint.
  2. Validate Project V2 token.
  3. Ensure the PR exists in the GitHub Project.
  4. Post the notification to Cliq.
  5. Save or reuse the PR thread id.
  6. Run AI Review Gate and publish the status check.
